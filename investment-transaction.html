Investment Transaction Platform

Desktop UX Design UI Design

An internal banking platform used by relationship managers at UOB to process investment transactions was built entirely around Unit Trusts. The business decided to expand it to cover four more products — bonds, structured deposits, structured notes, and insurance. Design was brought in to execute that plan.

From the first meetings, something felt wrong. Unit Trusts allow bulk transactions — an RM can select multiple and submit together. Bonds don't. One bond per transaction. These aren't style differences — they're different transaction models. The platform had been built around one of them.

Before designing anything, we pushed for an audit. Not a long one — focused on the three journeys most at risk. We presented the findings visually: the existing platform on one side, a projection of what five products stacked on top of it on the other. Stakeholders could see the problem. A written argument about scalability risk is easy to defer. A screen showing it isn't.

My Role

I was the lead product designer, one of two on the team. I owned the platform-level thinking — the overview navigation model, the shared structure across products, and the action hierarchy system. My co-designer handled detailed screen execution.

I ran briefing sessions with the business team, design reviews with the design head, and scope negotiations with the PM and stakeholders across seven two-week sprints.

Key Design Decisions

The audit ran against one question: if we add four products on top of this structure, what breaks? Three things came back — and each decision below was a direct response to one of them.

Decision 01

Turned the overview from a feed into a workbench

The original overview stacked all order types in one scrollable screen — Unit Trusts, bonds, structured products, all visible at once in separate sections. As products multiplied, finding relevant work meant scrolling past everything else first. The instinct was to fix this by adding more tabs.

More tabs would have made the navigation wider without making it smarter. Instead, I regrouped the page around how RMs actually worked: by what action they were taking (Buy/Switch, Sell, Instructions), then filtered by lifecycle state within each group. The context shift is the primary choice — the product is a secondary detail.

This also gave the platform a navigation model that could absorb future products. A new product type slots into an existing transaction family rather than requiring a new top-level section.

Decision 02

Gave every product a shared structure without forcing shared flows

The team's initial instinct was to either build separate screens per product, or use one generic table for all of them. Separate screens fragment the platform — it starts to feel like multiple tools. One table loses the product-specific detail RMs need to do their job.

I designed a common structural pattern: same page layout, same information hierarchy, same slot for product-specific detail. A bond screen and a Unit Trust screen use the same skeleton. The product fills in differently, but the platform feels like one tool.

The sharpest friction point was checkboxes. Midway through the project, the system architect pushed for full UI consistency — checkboxes on every product screen, regardless of transaction type. Our position: checkboxes communicate multi-select. A checkbox next to a single bond tells the user they can pick more. They can't. That's not a style question — it's a false affordance.

We built it as a rule: checkboxes appear only when multiple records exist in the list. One bond — no checkbox. Two bonds — checkboxes appear, but selecting one disables the other to prevent submitting two transactions the system can't process. The architect accepted it not as a compromise but as a consistent rule. It went into the design system as a platform-level decision, not a per-product judgment call.

Decision 03

Rebuilt the action hierarchy before it accumulated more debt

The platform had grown its button set product by product, sprint by sprint. By the time we started, there was no principled rule for where a primary, secondary, or utility action should live. Different lifecycle states, different products — different patterns everywhere.

I mapped every action across all lifecycle states and all product types, then defined an explicit rule: one primary action per screen — always the most important next step. Secondary actions support or modify it. Utilities (print, export, history) live in a separate zone that doesn't compete with the main path.

The rule was codified into the design patterns so future products had a framework to follow, not just a screen to copy. This was the work that mattered most for long-term scalability.

Outcome

The platform shipped across all seven sprints. The structural changes held — adding a new product type required a new product section, not a new overview design or a new action pattern.

One finding came from prototype testing that nothing in the BRD had flagged: RMs were reading the submit button as a confirmation — the final step. But submit was a trigger. It sent the transaction into a review queue. The distinction was invisible in the UI. We caught it because someone paused on a prototype. An explicit review state before submission fixed it.

The audit was the value. Not the screens. If we had accepted the lift-and-shift brief and started designing, we would have delivered five broken journeys on time. The decision to push for an audit before touching structure — that's what made the rest of the work matter.
